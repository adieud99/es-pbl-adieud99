# 3교시 실습 — 전문 검색 확장

공통 문제 1~3은 강사님 배포 데이터인 `products` index로, 개인 문제 4~5는 내 PBL index인
`flights`로 실행했다. 실행 시각은 2026-09-02 12:05~12:25 KST, Elasticsearch 9.5.0이다.

## (공통) 문제 1 — 제공 코드로 여러 field 검색

```http
GET /products/_search
{
  "size": 5,
  "query": {
    "multi_match": {
      "query": "무선 이어폰",
      "fields": ["name", "description"]
    }
  }
}
```

### 결과 입력

- `hits.total.value`: 505
- 상위 3개 ID·name: `P-00241` "SoundLab 프리미엄 무선 이어폰" / `P-00305` "Auralis 실속형 무선 이어폰" /
  `P-00529` "NeoTech 스마트 무선 이어폰" (셋 다 `_score` 6.7587247로 같다)
- 각 문서가 name·description 중 어디에서 의도와 연결되는가: **전부 `name`에서만 연결된다.**
  세 문서의 `description`은 "재택 학습에 잘 어울리는 전자기기 상품입니다", "여행에 잘 어울리는
  전자기기 상품입니다"처럼 용도만 적혀 있고 "무선"이나 "이어폰"이라는 단어가 없다.
  실제로 `match description "무선"`과 `match description "이어폰"`을 따로 실행하니 **둘 다 0건**이었다.
  `fields`에 `description`을 넣었지만 이 검색어에 대해서는 한 건도 기여하지 않는다.
- 상위 3개 관련/보류/무관 판정: 3건 모두 **관련**. `name`에 "무선"과 "이어폰"이 모두 들어 있고
  카테고리도 전자기기다. 사용자가 찾는 물건이 맞다.

`hits.total.value` 505는 `match name "무선"`의 505와 같은 값이다. `name`에 "이어폰"이 있는 문서는
249건인데 이들은 모두 "무선 이어폰"이라 무선 쪽에 이미 포함된다. 기본 `operator`가 `or`라
두 단어 중 하나만 걸려도 들어오므로, "무선 청소기"처럼 이어폰이 아닌 상품도 505건 안에 있다.

## (공통) 문제 2 — field boost 직접 구현

문제 1과 같은 조건을 유지하되 `name` 일치를 `description`보다 3배 중요하게 보는 Search API를 작성하세요.

### API 전체 입력

```http
GET /products/_search
{
  "size": 5,
  "_source": ["product_id", "name"],
  "query": {
    "multi_match": {
      "query": "무선 이어폰",
      "fields": ["name^3", "description"]
    }
  }
}
```

### 비교 결과

- 변경 전 상위 3개 ID: `P-00241`, `P-00305`, `P-00529`
- 변경 후 상위 3개 ID: `P-00241`, `P-00305`, `P-00529` — **하나도 바뀌지 않았다.**
  `hits.total.value`도 505로 같다.
- 순위가 달라진 문서와 이유: 없다. 달라진 것은 `_score`뿐으로 6.7587247에서 20.276176으로
  정확히 3배가 됐다. 순위가 그대로인 이유는 문제 1에서 확인한 대로 `description`이 이 검색어에
  아무 점수도 주지 않기 때문이다. 모든 문서가 `name`에서만 점수를 받고 있으니, 그 `name`
  점수에 다 같이 3을 곱해도 서로의 순서는 변하지 않는다.
- boost가 사용자 의도에 유리했는가: **이 데이터에서는 유리하지도 불리하지도 않았다.**
  boost는 두 field가 서로 다른 문서에 점수를 줄 때 어느 쪽을 더 믿을지 정하는 장치다.
  지금은 경쟁하는 field가 하나뿐이라 조정할 대상이 없다. `description`에 상품 특징이 문장으로
  들어 있는 데이터였다면 의미가 있었을 것이다. boost를 넣었는데 순위가 그대로라면 실패가
  아니라 **그 field가 실제로 매칭에 참여하고 있는지부터 확인해야 한다는 신호**로 읽어야 한다.

## (공통) 문제 3 — 구문 검색 직접 구현

`products` index의 `name`에서 `무선 이어폰`이라는 단어 순서와 인접성을 중요하게 검색하세요. `slop`은 0, 최대 5건으로 구현하세요.

### API 전체 입력

```http
GET /products/_search
{
  "size": 5,
  "_source": ["product_id", "name"],
  "query": {
    "match_phrase": {
      "name": {
        "query": "무선 이어폰",
        "slop": 0
      }
    }
  }
}
```

### 결과 입력

- `hits.total.value`: 249
- 상위 문서 ID·name: `P-00241` "SoundLab 프리미엄 무선 이어폰" / `P-00305` "Auralis 실속형 무선 이어폰" /
  `P-00529` "NeoTech 스마트 무선 이어폰" / `P-00617` "NeoTech 스마트 무선 이어폰" /
  `P-00777` "NeoTech 프리미엄 무선 이어폰"
- 문제 1보다 결과가 같거나 줄어든 이유: 505에서 249로 **256건 줄었다.** 문제 1의 `or`는 두 단어
  중 하나만 있어도 통과시키지만, `match_phrase`는 "무선"과 "이어폰"이 **이 순서로 바로 붙어**
  있어야 한다. `slop: 0`이라 사이에 다른 단어가 끼는 것도 허용하지 않는다. 빠진 256건은
  "CleanMate 실속형 무선 청소기"처럼 "무선"만 있는 문서다. `name`에 "이어폰"이 들어간 문서가
  249건인데 phrase 결과와 정확히 같으므로, 이 데이터의 이어폰은 전부 "무선 이어폰" 형태다.
- 구문 의도에 맞지 않는 문서가 있는가: 없다. 반환된 5건 모두 `name` 끝이 "무선 이어폰"이다.
  다만 이 데이터는 상품명이 "브랜드 + 수식어 + 품목" 틀로 생성돼 있어 두 단어가 항상 붙어
  나온다. 실제 서비스라면 "이어폰(무선)"처럼 순서가 뒤집힌 표기를 phrase가 놓칠 수 있다.
  그때는 `slop`을 올리거나 `match`와 함께 써야 한다.

## (개인) 문제 4 — 여러 text field 검색

자기 프로젝트에서 같은 사용자 검색어가 적용될 수 있는 text field 2개 이상을 선택해 전문 검색을 구현하세요.

### 역할·검증 기준

- 각 field의 서비스 역할을 설명합니다.
- 상위 3개 문서를 사람이 평가합니다.
- 한 field만 필요한 도메인이라면 `match`를 선택하고 그 이유를 적어도 됩니다.

### API와 결과 입력

```http
GET /flights/_search
{
  "size": 3,
  "_source": ["trip_id", "route_desc", "airline"],
  "query": {
    "multi_match": {
      "query": "대한항공 도쿄",
      "fields": ["route_desc", "airline"]
    }
  }
}
```

- 사용자 질문·검색어: "대한항공으로 가는 도쿄 항공권이 있나" / 검색어 "대한항공 도쿄"

- 선택 field와 역할:

| field | type | 서비스에서 맡는 역할 |
|---|---|---|
| `route_desc` | `text` | "인천 도쿄 왕복 직항"처럼 어디를 어떻게 가는지를 담는다. 사용자가 도시명·직항 여부를 이 문장에서 찾는다 |
| `airline` | `text` + `keyword` | 항공사명. 사용자는 문장 안에서 "대한항공"을 검색하지만 Dashboard에서는 `airline.keyword`로 정확히 묶어 센다 |

  검색어 하나에 두 field가 필요한 이유는 사용자가 "대한항공 도쿄"처럼 **성격이 다른 단어를
  한 줄에 섞어서** 입력하기 때문이다. "도쿄"는 `route_desc`에만 있고 "대한항공"은 `airline`에만
  있다. 한 field만 보면 둘 중 하나는 반드시 놓친다.

- 상위 3개 판정: `hits.total.value` 3,269 / 상위 3개는 `TRIP-00001`, `TRIP-00002`, `TRIP-00006`
  (`_score` 1.7776606로 동일)

| ID | `route_desc` | `airline` | 판정 |
|---|---|---|---|
| `TRIP-00001` | 인천 도쿄 왕복 경유 | 티웨이항공 | **보류**. 도쿄는 맞지만 대한항공이 아니다 |
| `TRIP-00002` | 인천 도쿄 왕복 직항 | 제주항공 | **보류**. 위와 같다 |
| `TRIP-00006` | 인천 도쿄 왕복 직항 | 진에어 | **보류**. 위와 같다 |

  상위 3건이 전부 "도쿄"만 만족하고 항공사는 틀렸다. 두 단어를 모두 만족하는 문서가 데이터에
  분명히 있는데도 위로 올라오지 못했다. 3,269라는 건수도
  1,690(도쿄) + 1,917(대한항공) − 338(둘 다) = 3,269로 계산이 맞는다. 기본 `operator`가 `or`라
  한쪽만 맞아도 들어온 결과다.

- query 선택 근거: 두 field가 모두 `text`이고 사용자가 단어 단위로 입력하므로 `match` 계열이
  맞다. field가 둘이라 `multi_match`를 골랐다. 2교시 문제 4의 `arr_airport`(`keyword`)처럼 값
  전체를 비교하는 상황이 아니다. 다만 아래 문제 5에서 보듯 `multi_match`는 field를 여러 개
  넘긴다고 해서 단어를 field에 나눠 배정해 주지는 않는다.

## (개인) 문제 5 — boost 또는 phrase 가설 검증

자기 검색에서 field boost 또는 phrase 중 하나를 선택해 기본 요청과 비교하세요.

### 역할·검증 기준

- 같은 index·데이터·검색어·size를 유지합니다.
- 한 요소만 변경합니다.
- 결과가 바뀌지 않아도 실제 결과대로 기록합니다.

### API와 결과 입력

```http
GET /flights/_search
{
  "size": 3,
  "_source": ["trip_id", "route_desc", "airline"],
  "query": {
    "multi_match": {
      "query": "대한항공 도쿄",
      "fields": ["route_desc", "airline^3"]
    }
  }
}
```

- 선택한 가설: 문제 4에서 항공사가 틀린 문서가 위로 왔으니, `airline`에 `^3` boost를 주면
  대한항공 문서가 상위로 올라와 사용자 의도에 가까워질 것이다. `fields`의 boost 값 하나만
  바꾸고 index·검색어·`size`·`_source`는 그대로 뒀다.

- 변경 전·후 상위 3개:

| 순위 | 변경 전 (boost 없음) | 변경 후 (`airline^3`) |
|---:|---|---|
| 1 | `TRIP-00001` 도쿄 경유 · 티웨이항공 | `TRIP-00003` **싱가포르** 직항 · 대한항공 |
| 2 | `TRIP-00002` 도쿄 직항 · 제주항공 | `TRIP-00014` **홍콩** 직항 · 대한항공 |
| 3 | `TRIP-00006` 도쿄 직항 · 진에어 | `TRIP-00019` **타이베이** 직항 · 대한항공 |

  `hits.total.value`는 3,269로 변하지 않았고 `_score`만 1.7776606에서 4.9549885로 올랐다.

- 개선/보류/악화 판정: **악화.**

- 판정 근거: 상위 3건이 전부 바뀌었으니 boost는 분명히 작동했다. 그런데 이번에는 항공사만
  맞고 **도착지가 전부 틀렸다.** 싱가포르·홍콩·타이베이가 올라왔다. 바뀐 것은 어느 쪽 오답을
  볼 것인가일 뿐이고, "대한항공이면서 도쿄"인 문서는 여전히 한 건도 상위에 없다.

  원인은 boost가 아니라 `or`였다. 점수를 조정해도 한 단어만 맞은 문서가 결과에서 빠지지는
  않는다. 그래서 `"operator": "and"`를 넣어 봤더니 이번에는 **0건**이 나왔다. `multi_match`의
  기본 type인 `best_fields`는 "한 field 안에서" 모든 단어를 찾기 때문이다. "대한항공"은
  `airline`에만, "도쿄"는 `route_desc`에만 있으니 두 단어를 모두 가진 field가 하나도 없다.

  `"type": "cross_fields"`와 `"operator": "and"`를 함께 주자 해결됐다. 이 type은 두 field를
  하나의 큰 field처럼 보고 단어를 나눠 찾는다.

| 요청 | total | 상위 1건 |
|---|---:|---|
| 기본 (`or`) | 3,269 | `TRIP-00001` 도쿄 경유 · 티웨이항공 |
| `airline^3` | 3,269 | `TRIP-00003` 싱가포르 직항 · 대한항공 |
| `best_fields` + `and` | 0 | — |
| `cross_fields` + `and` | **338** | `TRIP-00020` 도쿄 직항 · **대한항공** |

  338건은 `bool.filter`로 만든 정답 집합(`airline.keyword = 대한항공` AND `arr_airport = NRT`)의
  338건과 정확히 같다. 상위 3건도 `TRIP-00020`·`TRIP-00047`·`TRIP-00075`로 모두 도쿄 직항
  대한항공이라 **관련**이다.

  이번 실험에서 배운 것은 boost가 순위를 바꾸는 장치이지 결과 집합을 바꾸는 장치가 아니라는
  점이다. 틀린 문서가 섞여 있는 문제를 점수로 풀려고 하면 오답의 종류만 바뀐다. 무엇을
  결과에 넣을지는 `operator`와 `type`이 정한다.
