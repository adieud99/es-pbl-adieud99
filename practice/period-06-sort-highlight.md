# 6교시 실습 — 정렬·highlight

공통 문제 1~3은 강사님 배포 데이터인 `products` index로, 개인 문제 4~5는 내 PBL index인
`flights`로 실행했다. 실행 시각은 2026-09-03 14:40~15:05 KST, Elasticsearch 9.5.0이다.

## (공통) 문제 1 — 제공 코드로 1·2차 정렬 확인

```http
GET /products/_search
{
  "size": 10,
  "_source": ["product_id", "name", "price", "rating", "in_stock"],
  "query": { "match": { "name": "무선" } },
  "sort": [
    { "rating": "desc" },
    { "price": "asc" }
  ]
}
```

### 결과 입력

- 상위 5개 ID / rating / price: `hits.total.value`는 505건이다.

| 순위 | ID | rating | price | name |
|---:|---|---:|---:|---|
| 1 | `P-03842` | 5.0 | 13,900 | SimpleDay 컴팩트 무선 청소기 |
| 2 | `P-08761` | 5.0 | 107,200 | MobiCore 컴팩트 무선 이어폰 |
| 3 | `P-07634` | 5.0 | 132,300 | HomeNest 프리미엄 무선 청소기 |
| 4 | `P-05962` | 5.0 | 138,300 | SimpleDay 컴팩트 무선 청소기 |
| 5 | `P-06457` | 5.0 | 184,900 | PixelWorks 데일리 무선 이어폰 |

- 1차 정렬이 올바른가: 올바르다. 상위 7건이 전부 rating 5.0이고 8위부터 4.9로 떨어진다
  (`P-05738` 4.9 / `P-05218` 4.9 / `P-08138` 4.9). rating이 높은 순으로 내려간다.

- rating 동률에서 2차 정렬이 적용된 사례: rating 5.0 그룹이 그대로 사례가 된다. 무선 검색
  결과 중 rating이 정확히 5.0인 문서를 따로 세어 보니 **7건**이었고, 그 7건의 price를
  오름차순으로 뽑으면 `[13900, 107200, 132300, 138300, 184900, 322100, 350900]`이다.
  문제 1 결과의 1~7위 price와 순서·값이 완전히 같다. rating이 같은 구간 안에서 price가
  낮은 것부터 나온다는 뜻이므로 2차 정렬이 실제로 작동했다.

  1위 `P-03842`가 13,900원이고 2위가 107,200원으로 거의 8배 차이 나는데도 위에 온 이유가
  이것이다. 가격이 순위를 정한 게 아니라 rating이 먼저고, 같은 rating 안에서만 가격이
  개입한다.

- 동률이 없다면 2차 정렬을 확인할 수 있는 방법: 이번에는 동률이 있어서 해당 없다. 만약
  없었다면 두 가지로 확인할 수 있다. 첫째, 1차 정렬 field로 `terms` 집계를 돌려 doc_count가
  2 이상인 값이 있는지 먼저 찾고 그 값으로 filter를 걸어 좁힌 뒤 정렬을 본다. 둘째, 1차
  정렬 field를 일부러 카디널리티가 낮은 field(예: `in_stock` 같은 boolean)로 바꿔 동률을
  강제로 만든다. 동률이 없으면 2차 정렬은 코드에만 있고 실행되지 않으므로, 동률을 먼저
  만들어야 검증이 가능하다.

## (공통) 문제 2 — 정렬 우선순위 교환

문제 1과 같은 검색 결과를 가격이 낮은 순서로 먼저 정렬하고, 가격이 같으면 평점이 높은 순서로 정렬하세요.

### API 전체 입력

```http
GET /products/_search
{
  "size": 10,
  "_source": ["product_id", "name", "price", "rating"],
  "query": { "match": { "name": "무선" } },
  "sort": [
    { "price": "asc" },
    { "rating": "desc" }
  ]
}
```

### 비교 결과

- 변경 후 상위 5개 ID / price / rating:

| 순위 | ID | price | rating | name |
|---:|---|---:|---:|---|
| 1 | `P-01490` | 10,900 | 2.9 | SimpleDay 컴팩트 무선 청소기 |
| 2 | `P-05738` | 12,900 | 4.9 | CleanMate 스마트 무선 청소기 |
| 3 | `P-05218` | 13,300 | 4.9 | LumiHome 실속형 무선 청소기 |
| 4 | `P-08586` | 13,700 | 2.3 | SimpleDay 스마트 무선 청소기 |
| 5 | `P-03842` | 13,900 | 5.0 | SimpleDay 컴팩트 무선 청소기 |

- 순서가 달라진 문서: 사실상 전부 달라졌다. 문제 1의 1위 `P-03842`는 여기서 5위로 내려갔고,
  문제 1의 2~5위(`P-08761` 107,200원 등)는 10위 안에 아예 들어오지 못했다. 반대로 여기 1위인
  `P-01490`은 rating이 2.9라서 문제 1에서는 한참 뒤에 있었다.

  두 결과에 공통으로 들어간 문서는 `P-03842`, `P-05738`, `P-05218`, `P-08138` 네 건인데
  순위가 전부 다르다.

- 검색 hit 집합도 달라졌는가: 달라지지 않았다. 두 요청 모두 `hits.total.value`가 **505**로
  같다. `query`를 건드리지 않고 `sort`만 바꿨기 때문이다. 정렬은 이미 뽑힌 505건을 어떤
  순서로 늘어놓을지만 정하고, 어떤 문서가 뽑히는지는 `query`가 정한다. 화면 상단에 보이는
  10건이 완전히 달라져서 다른 검색처럼 보이지만 대상 집합은 같다.

  2차 정렬도 실제로 걸리는지 확인했다. 무선 검색 결과에서 price가 겹치는 값을 `terms`
  집계로 찾으니 34,500원이 2건 있었고, 그 두 건을 뽑아 보면 rating 내림차순으로 정렬된다.

| ID | price | rating | name |
|---|---:|---:|---|
| `P-07633` | 34,500 | 4.2 | SoundLab 실속형 무선 이어폰 |
| `P-08073` | 34,500 | 4.1 | PixelWorks 프리미엄 무선 이어폰 |

  4.2가 4.1보다 앞에 왔으므로 `rating: desc`가 적용됐다.

## (공통) 문제 3 — highlight와 표시 field 구현

`name`, `description`에서 `무선 이어폰`을 검색하되 `name`에 3배 boost를 적용하세요. 최대 5건을 반환하고 결과 카드용 field만 `_source`에 포함하며 `name`, `description`에 highlight를 적용하세요.

### API 전체 입력

```http
GET /products/_search
{
  "size": 5,
  "_source": ["product_id", "name", "price", "rating", "in_stock"],
  "query": {
    "multi_match": {
      "query": "무선 이어폰",
      "fields": ["name^3", "description"]
    }
  },
  "highlight": {
    "fields": {
      "name": {},
      "description": {}
    }
  }
}
```

### 결과 입력

- `_source` field 목록: `product_id`, `name`, `price`, `rating`, `in_stock` 다섯 개다.
  상품 카드에 필요한 최소 정보로 잡았다. 식별자, 상품명, 가격, 평점, 구매 가능 여부다.
  `description`은 카드에 안 보여줄 거라 `_source`에서 뺐는데, 그래도 검색 대상과 highlight
  대상에는 넣었다. 이게 가능하다는 것 자체가 이번 문제의 핵심이다.

- highlight가 생성된 문서 ID와 field: `hits.total.value` 505건, `max_score` 20.2762.
  상위 5건은 모두 `name`에만 highlight가 생성됐다.

| ID | _score | highlight[name] |
|---|---:|---|
| `P-00241` | 20.2762 | SoundLab 프리미엄 `<em>`무선`</em>` `<em>`이어폰`</em>` |
| `P-00305` | 20.2762 | Auralis 실속형 `<em>`무선`</em>` `<em>`이어폰`</em>` |
| `P-00529` | 20.2762 | NeoTech 스마트 `<em>`무선`</em>` `<em>`이어폰`</em>` |
| `P-00617` | 20.2762 | NeoTech 스마트 `<em>`무선`</em>` `<em>`이어폰`</em>` |
| `P-00777` | 20.2762 | NeoTech 프리미엄 `<em>`무선`</em>` `<em>`이어폰`</em>` |

  `description` highlight는 한 건도 없다. 이유를 확인해 보니 `description`에 "이어폰"이
  들어간 문서가 **0건**, "무선"이 들어간 문서도 **0건**이었다. 실제 값을 보면
  "출근에 잘 어울리는 패션 상품입니다. 사용 편의성과 실용성을 함께 고려했습니다." 같은
  일반 문구라서 상품명 단어가 아예 안 들어 있다. `description`을 검색 field에 넣긴 했지만
  이 데이터에서는 기여하는 게 없다.

- `_source`와 highlight의 차이: `_source`는 저장된 원본 값을 그대로 돌려주고, highlight는
  그 값 중 검색어와 맞은 부분에 `<em>` 태그를 감싼 **조각**을 따로 만들어 준다. 원본이
  바뀌는 게 아니라 표시용 복사본이 하나 더 오는 것이다.

  그래서 둘은 서로 독립적이다. 이번 요청이 그 증거인데, `description`은 `_source`에서
  제외했지만 highlight 대상으로는 지정돼 있다. 만약 `description`에 검색어가 있었다면
  원본은 안 받으면서 강조 조각만 받을 수 있었다. 반대로 `name`처럼 둘 다 받으면
  원본(`SoundLab 프리미엄 무선 이어폰`)과 강조본(`SoundLab 프리미엄 <em>무선</em>
  <em>이어폰</em>`)을 같이 갖게 된다.

- highlight가 없는 hit가 있다면 이유 추정: 없었다. 505건 중 뒤쪽 100건(`from: 405`)까지
  확인했는데 highlight가 없는 hit는 0건이었다. 마지막 문서도
  `LumiHome 프리미엄 <em>무선</em> 청소기`처럼 강조가 붙는다.

  없는 게 당연하다. `description`이 아무것도 못 맞추므로 505건은 전부 `name`으로 걸린
  문서이고, `name`은 highlight 대상에 포함돼 있어서 강조할 부분이 반드시 존재한다. 만약
  검색 field에는 있는데 highlight field에 안 넣은 field로만 매칭된 문서가 있었다면 그때
  highlight가 빈 hit가 나온다.

- boost 확인(추가): `name^3`이 순위를 바꾸는지 궁금해서 boost를 빼고 같은 요청을 돌려 봤다.

| fields | total | 상위 3 _score | 상위 3 ID |
|---|---:|---|---|
| `["name^3", "description"]` | 505 | 20.2762 | `P-00241`, `P-00305`, `P-00529` |
| `["name", "description"]` | 505 | 6.7587 | `P-00241`, `P-00305`, `P-00529` |

  20.2762 ÷ 3 = 6.7587로 정확히 3배다. 순위는 하나도 안 바뀌었다. boost는 여러 field가
  **경쟁할 때** 어느 쪽 매칭을 더 쳐줄지 정하는 장치인데, 여기서는 `description`이 아무것도
  못 맞춰서 경쟁 자체가 없다. 그래서 모든 문서의 점수가 똑같이 3배 되고 상대 순서는
  그대로다. boost를 넣었다고 항상 순위가 달라지지는 않는다는 걸 확인했다.

## (개인) 문제 4 — 자기 결과 정렬·카드 설계

자기 서비스에서 중요한 1차·2차 정렬 기준과 결과 카드 field 3~5개를 선택해 Search API를 구현하세요.

### 역할·검증 기준

- 정렬 가능한 mapping type을 사용합니다.
- 1차·2차 정렬의 업무적 이유를 설명합니다.
- 실제 상위 5개 값으로 순서를 검증합니다.

### API와 결과 입력

```http
GET /flights/_search
{
  "size": 5,
  "_source": ["trip_id", "airline", "route_desc", "seat_class", "total_price", "out_dep_time", "stay_nights"],
  "query": { "match": { "route_desc": "직항" } },
  "sort": [
    { "total_price": "asc" },
    { "out_dep_time": "asc" }
  ]
}
```

- 정렬 field·방향·이유: 1차는 `total_price` 오름차순, 2차는 `out_dep_time` 오름차순이다.

| 순서 | field | type | 방향 | 업무적 이유 |
|---:|---|---|---|---|
| 1차 | `total_price` | integer | asc | 항공권을 고를 때 제일 먼저 보는 게 가격이다. 싼 것부터 보여줘야 한다 |
| 2차 | `out_dep_time` | date | asc | 가격이 같으면 빨리 떠나는 편이 낫다. 출발이 임박한 특가부터 노출한다 |

  둘 다 정렬 가능한 type이다. `total_price`는 `integer`, `out_dep_time`은 `date`라
  doc_values로 바로 정렬된다. 반면 `route_desc`는 `text`라 분석돼서 쪼개지므로 정렬에
  쓸 수 없고, `airline`도 `text`지만 `airline.keyword` 서브필드가 있어서 그쪽으로는
  가능하다.

  `_score`를 1차로 쓰지 않은 이유가 있다. 쿼리가 `match route_desc "직항"` 하나뿐이라
  걸린 문서 대부분이 같은 점수를 받는다. 점수로 줄을 세워도 사실상 무작위 순서가 되므로
  사용자에게 의미 있는 기준인 가격을 앞에 뒀다.

- 카드 field와 이유: `trip_id`, `airline`, `route_desc`, `seat_class`, `total_price`,
  `out_dep_time`, `stay_nights` 일곱 개다. 문제는 3~5개를 요구했는데, 정렬 검증을 위해
  정렬 field 두 개를 반드시 봐야 해서 그만큼 늘렸다. 실제 서비스 카드라면 `trip_id`,
  `airline`, `route_desc`, `total_price` 네 개로 충분하다. 나머지 셋은 이번 검증용이다.

- 상위 5개 정렬 검증: `hits.total.value` **6,974건**.

| 순위 | ID | total_price | out_dep_time | seat_class | airline | route_desc |
|---:|---|---:|---|---|---|---|
| 1 | `TRIP-05865` | 300,113 | 2026-09-17T14:15:15Z | economy | 진에어 | 인천 오사카 왕복 직항 |
| 2 | `TRIP-02382` | 300,471 | 2026-09-01T22:52:30Z | economy | 아시아나항공 | 인천 도쿄 왕복 직항 |
| 3 | `TRIP-08027` | 300,510 | 2026-09-19T09:36:55Z | business | 티웨이항공 | 인천 홍콩 왕복 직항 |
| 4 | `TRIP-09904` | 300,562 | 2026-09-17T20:17:11Z | economy | 진에어 | 인천 방콕 왕복 직항 |
| 5 | `TRIP-03930` | 300,612 | 2026-09-08T09:20:33Z | economy | 제주항공 | 인천 방콕 왕복 직항 |

  가격이 300,113 → 300,471 → 300,510 → 300,562 → 300,612로 오름차순이다. 1차 정렬은
  맞는다. 다섯 건 모두 `route_desc`에 "직항"이 들어 있어 쿼리 조건도 만족한다.

  다만 상위 5건은 가격이 전부 달라서 2차 정렬이 개입할 자리가 없다. 출발 시각이
  09-17 → 09-01 → 09-19로 뒤죽박죽인데 이게 정상이다. 가격이 다르면 2차는 보지 않는다.
  2차 정렬 검증은 문제 1에서 배운 대로 동률을 먼저 찾아서 했다. `terms` 집계로 가격이
  겹치는 값을 찾으니 333,367원이 2건 있었다.

| ID | total_price | out_dep_time | route_desc |
|---|---:|---|---|
| `TRIP-07279` | 333,367 | 2026-09-14T19:35:55Z | 인천 홍콩 왕복 직항 |
| `TRIP-01833` | 333,367 | 2026-09-21T04:43:59Z | 인천 방콕 왕복 직항 |

  09-14가 09-21보다 앞에 왔으므로 `out_dep_time: asc`가 걸렸다. 노선이 홍콩과 방콕으로
  다른데 가격이 1원 단위까지 같은 건 운임을 난수로 생성했기 때문이고,
  `docs/data-model.md` 6절에 적어 둔 한계다.

## (개인) 문제 5 — 자기 highlight 또는 표시 최적화

자기 text 검색에 highlight를 적용하세요. text 검색이 없는 프로젝트라면 `_source` 최소화 전후를 비교하세요.

### 역할·검증 기준

- 검색 field와 highlight field의 관계가 타당해야 합니다.
- 원본 데이터와 강조 조각을 구분합니다.
- 사용자 판단에 실제로 도움이 되는지 평가합니다.

### API와 결과 입력

```http
GET /flights/_search
{
  "size": 5,
  "_source": ["trip_id", "airline", "route_desc", "total_price"],
  "query": {
    "multi_match": {
      "query": "직항 도쿄",
      "fields": ["route_desc^2", "airline"]
    }
  },
  "highlight": {
    "fields": {
      "route_desc": {},
      "airline": {}
    }
  },
  "sort": [
    { "_score": "desc" },
    { "total_price": "asc" }
  ]
}
```

- 선택한 방식과 이유: highlight를 골랐다. `flights`에 `text` field가 `route_desc`와
  `airline` 둘 있어서 전문 검색이 가능하다.

  검색 field와 highlight field를 똑같이 맞췄다. 사용자가 입력창에 "직항 도쿄"라고 쳤을 때
  왜 이 결과가 나왔는지를 보여주려는 것이므로, 검색한 곳과 강조하는 곳이 어긋나면 안 된다.
  검색은 했는데 강조를 안 하면 사용자는 이유를 모르고, 검색 안 한 field를 강조하면
  실제 매칭과 다른 곳에 밑줄이 그어진다.

  `route_desc`에 2배 boost를 준 것은 노선 정보가 항공사명보다 검색 의도에 가깝다고 봤기
  때문이다. "도쿄"를 친 사람은 도쿄행을 찾는 것이지 도쿄라는 항공사를 찾는 게 아니다.

- 실제 결과: `hits.total.value` **7,497건**. 상위 5건은 모두 `_score` 4.2762로 같아서
  2차 정렬인 `total_price` 오름차순이 순서를 정했다.

| ID | _score | total_price | airline | highlight[route_desc] |
|---|---:|---:|---|---|
| `TRIP-02382` | 4.2762 | 300,471 | 아시아나항공 | 인천 `<em>`도쿄`</em>` 왕복 `<em>`직항`</em>` |
| `TRIP-07275` | 4.2762 | 301,046 | 대한항공 | 인천 `<em>`도쿄`</em>` 왕복 `<em>`직항`</em>` |
| `TRIP-00422` | 4.2762 | 301,226 | 아시아나항공 | 인천 `<em>`도쿄`</em>` 왕복 `<em>`직항`</em>` |
| `TRIP-00200` | 4.2762 | 301,950 | 아시아나항공 | 인천 `<em>`도쿄`</em>` 왕복 `<em>`직항`</em>` |
| `TRIP-02815` | 4.2762 | 303,537 | 아시아나항공 | 인천 `<em>`도쿄`</em>` 왕복 `<em>`직항`</em>` |

  1위 `TRIP-02382`의 원본과 강조본을 나란히 보면 차이가 분명하다.

  - `_source`: `{"trip_id": "TRIP-02382", "route_desc": "인천 도쿄 왕복 직항", "airline": "아시아나항공", "total_price": 300471}`
  - `highlight`: `{"route_desc": ["인천 <em>도쿄</em> 왕복 <em>직항</em>"]}`

  `_source`의 `route_desc`는 태그가 없는 원본 그대로다. highlight는 같은 문장에 태그만
  입힌 별도 값이고, `airline` 키는 아예 없다. 이 검색어로는 항공사가 안 맞았기 때문이다.
  highlight는 맞은 field만 돌려준다.

  7,497건이 어떻게 나온 건지도 확인했다. 두 단어를 OR로 찾으므로 셋으로 나뉜다.

| 조합 | 건수 |
|---|---:|
| 도쿄 + 직항 둘 다 | 1,167 |
| 도쿄만 (경유편) | 523 |
| 직항만 (다른 노선) | 5,807 |
| 합계 | **7,497** |

  실제 total과 정확히 맞는다. 상위 300건을 확인하니 전부 두 단어가 강조된 문서였고,
  하위권(`from: 7400`)으로 내려가면 한 단어만 강조된 문서가 나온다. `TRIP-09818`은
  `인천 방콕 왕복 <em>직항</em>`으로 "직항"만 강조되고 score가 0.7208로 뚝 떨어진다.
  두 단어가 맞은 문서가 위로, 하나만 맞은 문서가 아래로 가는 게 강조 개수로 눈에 보인다.

  `airline`에도 highlight가 걸리는지 확인하려고 검색어를 "대한항공 직항"으로 바꿔 봤다.
  `TRIP-00003`은 `{"airline": ["<em>대한항공</em>"], "route_desc": ["인천 싱가포르 왕복 <em>직항</em>"]}`으로
  두 field에 동시에 강조가 붙었다. field 여러 개를 highlight 대상으로 지정하면 맞은
  것마다 각각 돌려준다는 걸 확인했다.

- 사용자에게 유용한가: 유용하다. 특히 부분 매칭일 때 그렇다. 7,497건 중 5,807건은 "도쿄"와
  아무 상관 없는 직항편인데, 화면에 `인천 방콕 왕복 <em>직항</em>`이라고 뜨면 사용자가
  "아 이건 도쿄가 아니라 직항만 맞은 거구나"를 바로 안다. 강조가 없으면 왜 방콕이 도쿄
  검색에 나오는지 이해하지 못하고 검색이 이상하다고 느낀다.

  가격 정렬과 조합했을 때도 도움이 된다. 상위 5건이 전부 300,471~303,537원으로 비슷한데
  점수도 같다. 이때 강조 개수가 같다는 걸 보면 "이 다섯 개는 조건상 동급이고 가격으로만
  갈린다"는 판단이 선다.

- 개선할 점: 세 가지가 보인다.

  첫째, `route_desc`가 `인천 도쿄 왕복 직항`처럼 짧아서 highlight의 장점이 덜 드러난다.
  긴 문장이면 `fragment_size`로 잘라 보여주는 게 의미가 있는데 지금은 문장 전체가
  그대로 나온다. 설명 문구 같은 긴 text field가 있었다면 더 잘 보였을 것이다.

  둘째, OR 매칭이라 관련 없는 결과가 너무 많다. 7,497건 중 도쿄가 실제로 들어간 건
  1,690건(1,167 + 523)뿐이다. `minimum_should_match`를 걸거나 `operator: and`로 바꾸면
  1,167건으로 좁힐 수 있다. 다만 그러면 "도쿄 경유편"이 빠지므로 서비스 성격에 따라
  판단할 문제다.

  셋째, 지금은 `<em>` 기본 태그를 쓰는데 실제 화면에서는 `pre_tags`/`post_tags`로
  프론트 CSS 클래스를 지정하는 편이 낫다. 태그를 그대로 innerHTML에 넣으면 XSS 위험이
  있어서 프론트에서 한 번 걸러야 한다는 것도 같이 확인했다.
