## (개인·필수) 문제 1 — 사용자 행동 두 가지 테스트

| 행동 | 시작 상태 | 적용 조건 | 변한 패널·값 | 사용자의 판단 | 복구 방법 | 복구 성공 |
|---|---|---|---|---|---|---|
| 1 | 전체 10,000, Control `Any` | Control = `진에어` | Metric 10,000→**2,063**, Donut 5분할→**진에어 100%**, 도착지 Bar SIN 1,691→**375**, Table 셀 5→**1**, Tag cloud SIN 부각, Heatmap 5행→**1행** | 진에어 물량이 전체의 20.6%다. 노선별로는 SIN 375가 가장 많고 TPE 327이 가장 적으므로, 타이베이 좌석을 추가 요청한다 | 드롭다운 `Any` | O (10,000) |
| 2 | 전체 10,000 | 도착지 Bar에서 `SIN` 막대 클릭 → filter pill `arr_airport: SIN` 생성 | Metric 10,000→**1,691**, Donut이 SIN 노선 항공사 구성으로, Table이 SIN 열만 남음 | 싱가포르 노선에 1,691개를 확보했다. 6개 노선 중 1위지만 NRT 1,690과 1건 차이라 사실상 동률이다. 특정 노선에 쏠려 있지 않다 | filter pill `×` | O (10,000) |

- 두 행동이 서로 다른 이유: **행동 1은 공급자 축, 행동 2는 노선 축**이다. 1은 "이 항공사가
  뭘 갖고 있나"를 묻고 2는 "이 노선을 누가 채우나"를 묻는다. 조작 방법도 다르다. 1은
  미리 만들어 둔 Control이고, 2는 차트를 클릭해 즉석에서 만드는 filter다.

- 사용자가 멈추거나 헷갈린 지점:
  1. **`Any`가 해제 버튼이 아니다.** Control을 지우려고 `×`를 찾는데 없다. `Any`로
     되돌리는 방식이라는 걸 모르면 막힌다.
  2. **Control과 filter가 겹칠 때.** 둘 다 걸어두면 어느 쪽 때문에 값이 변했는지
     알 수 없다. 실제로 `dep_airport: exists` filter를 걸어뒀다가 이 문제를 겪고 지웠다.
  3. **히트맵 색이 필터마다 다시 계산된다.** 전후 캡처에서 같은 빨강인데 기준값이
     331.8과 346.2로 다르다.

- 캡처 파일:

| 파일 | 상태 |
|---|---|
| `picture/p05-q03-baseline.png` | 조건 없음, Metric 10,000 |
| `evidence/day-04/personal-dashboard-filtered.png` | 행동 1 — Control 진에어, 2,063 |
| `picture/p08-q01-action2-sin.png` | 행동 2 — filter `arr_airport: SIN`, 1,691 |

  행동 2의 1,691은 `GET /flights/_count`에 `term arr_airport:SIN`을 걸어 대조했고 일치한다.

## (개인·필수) 문제 2 — 핵심값 3개 교차 검증

시간 범위 `This year`, KQL 없음, Control `Any` 상태로 맞춘 뒤 비교했다.

| Dashboard 패널·값 | 동일하게 맞춘 시간·조건 | 비교 방법 | 비교값 | 일치 | 다르면 원인 |
|---|---|---|---:|---|---|
| 1. 항공편수 Metric **10,000** | This year, 조건 없음 | `GET /flights/_count` | 10,000 | **일치** | — |
| 2. 항공사 Donut 진에어 **20.63%** | 〃 | `terms` on `airline.keyword` | 2,063 / 10,000 = 20.63% | **일치** | — |
| 3. 도착지 Bar SIN **1,691** | 〃 | `terms` on `arr_airport` | 1,691 | **일치** | — |

추가로 Control 적용 상태도 대조했다.

| Dashboard 값 | 비교 방법 | 비교값 | 일치 |
|---|---|---:|---|
| 진에어 Metric **2,063** | `_count` + `term airline.keyword:진에어` | 2,063 | 일치 |
| 진에어 SIN 막대 **375** (툴팁) | 위 조건 + `terms` on `arr_airport` | 375 | 일치 |

도넛 다섯 조각이 전부 소수점 둘째 자리까지 맞았다.

| airline | 화면 | 계산 |
|---|---:|---:|
| 진에어 | 20.63% | 2,063 / 10,000 |
| 아시아나항공 | 20.31% | 2,031 / 10,000 |
| 제주항공 | 19.96% | 1,996 / 10,000 |
| 티웨이항공 | 19.93% | 1,993 / 10,000 |
| 대한항공 | 19.17% | 1,917 / 10,000 |

- 비교에 사용한 요청 파일 또는 Discover 캡처: 아래 요청과 `picture/p05-q03-*.png` 세 장.

```http
GET /flights/_count

GET /flights/_search
{
  "size": 0,
  "aggs": {
    "by_airline": { "terms": { "field": "airline.keyword", "size": 5, "order": { "_count": "desc" } } },
    "by_arr":     { "terms": { "field": "arr_airport",     "size": 6, "order": { "_count": "desc" } } }
  }
}

GET /flights/_search
{
  "size": 0,
  "query": { "term": { "airline.keyword": "진에어" } },
  "aggs": { "by_arr": { "terms": { "field": "arr_airport", "size": 6, "order": { "_count": "desc" } } } }
}
```

- 세 값을 신뢰할 수 있는 이유: 세 가지가 서로를 받쳐준다.
  1. **합이 맞는다.** 도착지 6개 합 = 10,000, 항공사 5개 합 = 10,000으로 Metric과 같다.
     잘린 값이 없다는 뜻이다.
  2. **다른 경로로 같은 값이 나온다.** Metric은 `_count`로, 나머지는 `terms` 집계로
     확인했다. 서로 다른 API가 같은 숫자를 준다.
  3. **필터 상태에서도 맞는다.** 진에어 2,063은 전체 집계의 진에어 버킷과 같고,
     그 안의 도착지 합(375+347+341+337+336+327 = 2,063)도 맞는다.

  Top N을 넉넉히 준 것도 중요했다. 3교시에서 `brand` Top 5로 두니
  `doc_count_error_upper_bound`가 253이 나와 1위가 틀렸다. `airline`은 5종, `arr_airport`는
  6종이라 그만큼 주면 오차가 0이 된다.

## (개인·필수) 문제 3 — 문제 하나를 실제로 수정하고 재검증

- 발견한 문제: 도착지 Bar의 y축 라벨이 `가격`인데 축의 값은 0~2,000 사이 **건수**였다.
- 문제 유형: **제목·라벨**
- 수정 전 설정 또는 결과: y축 `가격`, 막대 최대 높이 1,691. 라벨대로 읽으면 "1,691원"이
  된다.
- 추정 원인: 패널을 만들 때 field를 여러 번 바꾸면서 이전 설정의 축 이름이 남았다.
  Lens는 field를 바꿔도 사용자가 지정한 label을 자동으로 갱신하지 않는다.
- 수정한 한 가지: y축 label을 `가격` → `상품 수`로 바꿨다. field·집계·Top N·정렬은
  건드리지 않았다.
- 수정 후 결과: 막대 높이는 그대로 1,691이고 라벨만 `상품 수`가 됐다. 값이 안 변한 게
  정상이다. label은 표시 텍스트일 뿐 집계에 영향을 주지 않는다.
- 같은 조건 재검증 결과: SIN 1,691 / NRT 1,690 / BKK 1,670 / HKG 1,666 / TPE 1,646 /
  KIX 1,637. 수정 전과 동일하고 `terms` 집계와도 일치한다.
- 개선/보류/악화 판정과 근거: **개선.** 숫자는 그대로인데 읽는 사람이 잘못 해석할 여지가
  사라졌다. 축 라벨은 그 축이 무엇을 재는지 말하는 유일한 단서라서, 틀리면 차트 전체가
  틀린 정보가 된다.
- 수정 전·후 캡처: 수정 전은 이전 캡처(15:18), 수정 후는
  `evidence/day-04/personal-dashboard.png`(15:47).

같은 방식으로 두 개를 더 고쳤다. 숙박일수 Line의 y축(`도착지` → `상품 수`)과
효과 없는 `dep_airport: exists` filter 제거다. 자세한 기록은 `dashboard-review.md` 6절에 있다.

## (개인·필수) 문제 4 — 결과 3·한계 2·필요 데이터 1과 제출

### 결과 3개

1. **조건**: 전체 10,000건, 조건 없음. **핵심값**: 항공사 5개가 1,917~2,063건.
   **비교**: 점유율이 19.17~20.63% 안에 들어오고 1위와 5위 차이가 146건.
   **판단**: 공급이 특정 항공사에 몰려 있지 않다. 한 곳에 의존할 위험이 낮으므로,
   협상에서 특정 항공사에 끌려갈 이유가 없다.

2. **조건**: Control = 진에어(2,063건). **핵심값**: SIN 375가 1위, TPE 327이 6위.
   **비교**: 전체에서는 SIN 1,691과 NRT 1,690이 1건 차이인데, 진에어만 보면 SIN 375와
   NRT 337로 38건 벌어진다. **판단**: 진에어에 타이베이 좌석 추가 확보를 요청한다.
   다만 아래 한계 2번 때문에 이 차이를 확정적으로 읽지는 않는다.

3. **조건**: 전체 10,000건. **핵심값**: 숙박일수 1~10일이 969~1,061건으로 균등.
   **비교**: 특정 기간에 몰린 구간이 없다. **판단**: 단기·장기 상품 비율을 조정할 근거가
   지금 데이터에는 없다. 판매 데이터를 확보한 뒤 다시 본다.

### 현재 데이터의 한계 2개

1. **판매를 모른다.** `out_dep_time`은 출발 예정일이지 판매일이 아니다. 상품이 몇 개
   있는지만 알고 팔렸는지 모른다. "물량이 많다"와 "재고가 남는다"를 구분할 수 없어서,
   소싱 담당자가 진짜 알고 싶은 "이 노선이 잘 나가나"에 답할 수 없다.

2. **field 사이에 관계가 없다.** `total_price`가 `seat_class`와 무관하게 30만~120만
   난수로 생성됐다. 셀별 평균 운임이 726,331~770,294로 6% 안에 들어와 등급 구분이 안 된다.
   퍼스트클래스가 30만원대로 나오는 문서도 있다. 같은 이유로 히트맵 30칸이 303~375에
   몰려 있어 색 차이가 난수 변동이다.

### 추가로 필요한 데이터 1개

- field: `booked_at`
- mapping type: `date`
- 예시값: `2026-08-20T14:22:10Z`, `2026-08-28T09:05:47Z`, `2026-09-01T20:41:03Z`
- 값 분포·생성 규칙: `out_dep_time` 기준 D-90 ~ D-1 사이. 반드시
  `booked_at < out_dep_time`이어야 한다. 10,000건을 90일에 뿌리면 하루 평균 111건이라
  일 단위 Line이 안정적으로 그려진다. seed를 고정해 재생성해도 같은 값이 나오게 한다.
- 추가되면 답할 수 있는 질문: **"언제 얼마나 팔렸나?"** 주간 판매 추이를 그릴 수 있고,
  `seats_sold`까지 있으면 노선별 소진 속도를 비교해 어디를 더 확보할지 정할 수 있다.
  지금은 확보량만 보고 추측하는데, 그러면 안 팔리는 노선을 계속 늘리는 판단을 할 수 있다.
