# ingest pipeline 적용 판단

## 결론

**미적용.** 정의와 `_simulate`로 동작은 확인하되, 이번 10,000건 Bulk 적재에는 연결하지 않는다.

## 판단 근거

이 PBL의 데이터는 생성 스크립트가 mapping에 맞는 형태로 직접 만든다. 색인 시점에 고쳐야
할 값이 없다. pipeline은 외부에서 들어오는 데이터의 모양이 내 mapping과 다를 때 서버 쪽에서
맞춰 주는 도구인데, 지금은 그 상황이 아니다.

생성 규칙을 고치면 되는 일을 pipeline으로 처리하면 변환 규칙이 스크립트와 pipeline 두 곳에
나뉘어 나중에 어느 쪽이 값을 바꿨는지 추적하기 어려워진다.

## 만약 적용한다면

실제 항공사 API에서 받은 데이터를 넣는 상황을 가정하면 다음이 대상이 된다.

| 대상 field | 입력 | 출력 | processor |
|---|---|---|---|
| `carrier_name` | 항공사명이 다른 이름으로 들어옴 | `airline` | `rename` |
| `is_direct` | 값이 없음 | `false` | `set` (override:false) |
| `raw_price`, `temp` | 원본에만 있는 임시 값 | 제거 | `remove` |

`set`에 `override:false`를 주는 이유는 이미 값이 있는 문서를 덮어쓰지 않기 위해서다.
값이 없을 때만 기본값을 넣는다.

## 처리 위치를 어디로 볼 것인가

| 위치 | 맞는 경우 |
|---|---|
| 생성 스크립트 / 애플리케이션 | 데이터를 내가 만들고 규칙을 한곳에서 관리할 때 |
| ingest pipeline | 여러 곳에서 들어오는 데이터를 색인 직전에 한 번에 맞출 때 |
| 검색 시점 | 원본을 그대로 두고 조회할 때만 다르게 보여야 할 때 |

이번 과제는 첫 번째에 해당한다. 반복 여부는 판단을 돕는 요소이지 기술적 제한은 아니다.

## 원본 보존

`remove`로 지운 field는 되돌릴 수 없다. 실제 운영이라면 원본 payload를 별도 index나 파일로
남긴 뒤 pipeline을 적용해야 한다. 이번에는 `_simulate`만 사용하므로 저장된 문서가 바뀌지 않는다.

## 확인한 것

`_simulate` 결과는 `evidence/day-02-data.md`의 T16에 기록한다. 정의를 저장하는 것만으로는
기존 문서가 바뀌지 않는다. 적용 요청이나 `default_pipeline` 설정으로 연결해야 동작하며,
공통 `products`에는 임의로 적용하지 않는다.
