# 데이터 모델

## 1. 문서 단위

- 검색 결과 한 건은 무엇인가: 인천 출발 왕복 항공권 1건 (가는 편과 오는 편이 짝지어진 조합)
- 이 문서 한 건이 사용자에게 보여 주는 정보는 무엇인가: 항공사, 도착 공항, 가는 편 출발 일시, 체류일수, 좌석등급, 왕복 총액, 직항 여부
- index 이름: `flights`
- 업무 ID field: `trip_id`
- 예시 ID: `TRIP-00001`

`trip_id`는 업무 ID이고 `_id`는 Elasticsearch 메타데이터다. 이 index에서는 같은 값을
쓰지만 자동으로 동기화되지는 않으므로, 생성 스크립트가 두 값을 함께 배정한다.

편도 1구간이 아니라 왕복 조합을 문서 단위로 잡은 이유는, 사용자가 실제로 고르는 대상이
"편 하나"가 아니라 "다녀오는 일정 하나"이기 때문이다.

오는 편 출발 일시는 별도 field로 두지 않는다. `out_dep_time`에 `stay_nights`를 더하면
계산할 수 있고, 따로 저장하면 두 값이 어긋날 수 있다.

## 2. 대표 문서 예시

```json
{
  "trip_id": "TRIP-00001",
  "route_desc": "인천 도쿄 왕복 경유",
  "airline": "티웨이항공",
  "dep_airport": "ICN",
  "arr_airport": "NRT",
  "seat_class": "business",
  "out_dep_time": "2026-09-15T23:46:28Z",
  "stay_nights": 5,
  "total_price": 924066,
  "is_direct": false,
  "tags": ["수하물포함", "할인"]
}
```

## 3. 질문 3개와 분해

| 번호 | 질문 | 검색어 | 조건 | 정렬 | 표시 | 필요 field |
|---:|---|---|---|---|---|---|
| 1 | "도쿄 직항" 항공권을 찾고 싶다 | 도쿄 직항 | — | — | 항공사·노선·총액 | `route_desc`, `airline` |
| 2 | 도쿄행 왕복 직항 이코노미 중 총액 50만원 이하를 싼 순으로 | — | `arr_airport`=NRT, `is_direct`=true, `seat_class`=economy, `total_price`≤500000 | `total_price` 오름차순 | 항공사·출발 일시·체류일수·총액 | `arr_airport`, `is_direct`, `seat_class`, `total_price` |
| 3 | 노선별·체류일수별 평균 총액은 얼마인가 | — | — | — | 집계 결과 | `arr_airport`, `stay_nights`, `total_price` |

## 4. 핵심 field와 역할

| field | 예시 값 | 검색에서 맡는 역할 | ES type | 연결 질문 | 선택 이유 |
|---|---|---|---|---|---|
| `trip_id` | TRIP-00001 | 업무 ID | `keyword` | — | 값 전체로 식별한다. 쪼갤 이유가 없다. |
| `route_desc` | 인천 도쿄 왕복 직항 | 전문 검색 | `text` | 1 | "도쿄 직항"처럼 단어로 입력받으므로 문장을 쪼갠다. |
| `airline` | 대한항공 | 전문 검색 / 집계 | `text` + `keyword` | 1 | 문장으로 검색하지만 항공사별로도 정확히 묶어 세야 한다. |
| `dep_airport` | ICN | 정확 조건 | `keyword` | 2 | 공항 코드는 쪼개면 의미가 없고 값 전체가 일치해야 한다. |
| `arr_airport` | NRT | 정확 조건 / 집계 | `keyword` | 2, 3 | 노선을 지정하고 노선별로 총액을 묶어 비교한다. |
| `seat_class` | economy | 정확 조건 / 집계 | `keyword` | 2 | 등급을 정확히 고르고 등급별로 묶는다. |
| `out_dep_time` | 2026-09-15T23:46:28Z | 범위 / 정렬 | `date` | 2 | 출발 주간과 시간대를 범위로 좁힌다. |
| `stay_nights` | 5 | 범위 / 집계 | `integer` | 3 | 며칠 일정인지 조건을 걸고 체류일수별로 총액을 본다. |
| `total_price` | 924066 | 범위 / 정렬 / 집계 | `integer` | 2, 3 | 예산 상한을 걸고 싼 순으로 정렬하며 평균을 낸다. |
| `is_direct` | false | 정확 조건 | `boolean` | 2 | 직항만 남기는 참·거짓 조건이다. |
| `tags` | ["수하물포함", "할인"] | 정확 조건 / 집계 | `keyword` | — | 같은 type의 값 여러 개이므로 배열 type을 따로 선언하지 않는다. |

`airline`을 `text`와 `keyword` 두 가지로 두는 것이 이 모델의 핵심이다. 사용자는
"대한항공"을 문장 안에서 검색하지만 Dashboard에서는 항공사별로 정확히 묶어 세야 한다.
두 요구가 하나의 type으로는 동시에 만족되지 않는다. 원본 JSON에 `airline.keyword`를
따로 넣지는 않는다. mapping의 `fields`가 하나의 입력에서 두 가지 색인을 만든다.

`is_direct`가 boolean이면서 `route_desc`에도 "직항"·"경유" 문구가 들어가는 이유는,
사용자가 두 가지 방식으로 찾기 때문이다. 조건으로 걸 때는 boolean이 정확하고, 문장으로
검색할 때는 `route_desc`가 걸린다. 생성 스크립트가 `is_direct`를 먼저 뽑고 그 값으로
`route_desc`를 만들기 때문에 두 값은 항상 일치한다.

`dynamic`은 `strict`로 둔다. 정의하지 않은 field가 들어오면 색인을 거부해서 생성 규칙과
mapping이 어긋나는 것을 바로 잡아낸다.

## 5. 제외할 데이터

- 수집하거나 저장하지 않을 개인정보: 승객 이름, 여권번호, 예약번호, 연락처, 결제 수단, 실제 예약 이력
- 제외 이유: 이 PBL은 항공권 자체를 검색하는 과제이며 개인정보가 필요하지 않다. 항공사·공항·운임은 모두 합성값을 사용한다.

## 6. 이 데이터 모델의 한계

운임이 노선·좌석등급과 무관하게 생성된다. 실제 항공권은 거리와 좌석등급에 따라 운임이
달라지지만 이 데이터는 세 값을 독립적으로 뽑는다. 따라서 등급별·노선별 가격 차이는 이
데이터로 검증하지 않는다. 자세한 내용은 `data/generation-notes.md` 6절에 있다.
