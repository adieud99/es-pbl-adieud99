# Dashboard 계획

## 1. Dashboard 사용자와 목적

- Dashboard를 볼 사용자: 출발일과 체류일수를 정하지 못한 여행객
- 이 사용자가 확인하려는 상황: 노선별 총액 수준과 체류일수에 따른 총액 변화
- Dashboard를 본 뒤 할 다음 행동:
  총액이 낮게 형성되는 노선과 체류일수를 확인하고 출발일을 조정한다.

## 2. 분석 질문

1. 노선별 평균 왕복 총액은 얼마인가?
2. 체류일수별 평균 왕복 총액은 얼마인가?

## 3. 차트 아이디어 초안

| 차트 아이디어 | 답할 질문 | 사용할 field 후보 |
|---|---|---|
| 노선별 평균 총액 막대 차트 | 어느 노선이 상대적으로 싼가? | `arr_airport`, `total_price` |
| 좌석등급 비율 차트 | 이코노미 좌석은 얼마나 되는가? | `seat_class` |

> 평가 최소 기준은 차트 2개 이상이지만, 수업에서는 차트 4개를 완성합니다.

## 4. Control과 시간 설정

- Options list 또는 range control에 사용할 field:
  Options list — `arr_airport`(도착 공항), `seat_class`(좌석등급), `is_direct`(직항 여부)
  Range slider — `total_price`(왕복 총액), `stay_nights`(체류일수)

- 이 control로 함께 좁힐 차트:
  노선별 평균 총액 막대 차트, 체류일수별 평균 총액 차트.
  좌석등급과 직항 여부가 섞인 채로 평균을 내면 사용자가 어느 조합이 싼지 판단할 수 없다.
  도착 공항이 6개이므로 특정 노선만 보고 싶을 때도 control이 필요하다.

- Data View 이름: `flights`

- 시간 field: 사용

- 시간 field를 사용한다면 field 이름과 기간:
  `out_dep_time`(가는 편 출발 일시), 기간은 2026-09-01 ~ 2026-09-30

  왕복이지만 날짜 field는 `out_dep_time` 하나다. 사용자가 기준 삼는 것은 "언제 떠나는가"이고,
  돌아오는 날짜는 체류일수로 표현된다.

## 5. 제목과 배치 계획

- Dashboard 제목: 왕복 항공권 총액 분석

- 상단에 둘 차트 또는 control:
  `arr_airport`·`seat_class` options list, `total_price` range slider,
  그리고 조건에 맞는 항공권 건수를 보여 주는 Metric

- 가운데에 둘 차트:
  노선별 평균 왕복 총액 막대 차트, 체류일수별 평균 총액 차트

- 하단에 둘 차트:
  가는 편 출발 시간대별 항공권 수 차트

control을 상단에 두는 이유는 사용자가 차트를 읽기 전에 범위를 좁히는 순서가 되어야 하기
때문이다. 아래에 두면 차트를 먼저 보고 나중에 좁히는 꼴이 되어 순서가 뒤집힌다.

### 계획과 다르게 바꾼 점 및 이유

**1. 지표를 평균 총액에서 건수로 바꿨다.** 이게 제일 큰 변경이다.

계획은 "어느 노선이 싼가"를 묻고 `total_price` 평균을 쓰려 했다. 실제로 계산해 보니
답이 나오지 않는 데이터였다.

| 도착지 | 평균 총액 | 체류일수 | 평균 총액 |
|---|---:|---:|---:|
| SIN | 762,745 | 1박 | 743,124 |
| NRT | 758,635 | 4박 | 759,884 |
| BKK | 752,855 | 7박 | 742,223 |
| HKG | 751,340 | 10박 | 748,232 |
| TPE | 739,990 | | |
| KIX | 739,074 | | |

노선 6개가 739,074~762,745로 **3% 안에 다 들어온다.** 체류일수는 더 심해서 폭이
17,661원(2%)뿐이다. 운임을 30만~120만 균등 난수로 생성했고 노선·체류일수와 아무 관계도
주지 않았기 때문이다. 이 상태로 "어느 노선이 싸다"고 말하면 근거 없는 결론이 된다.

그래서 지표를 건수로 바꾸고 질문도 "어느 노선에 물량이 얼마나 있나"로 옮겼다. 이건
데이터가 실제로 답할 수 있는 질문이다.

**2. 사용자를 여행객에서 소싱 담당자로 바꿨다.**

1번의 결과다. 가격 비교가 안 되니 여행객에게 줄 정보가 없다. 대신 "어느 항공사가 어느
노선을 얼마나 들고 있나"는 답할 수 있어서, 상품을 확보하는 쪽으로 사용자를 옮겼다.

**3. control을 `arr_airport`·`seat_class`에서 `airline.keyword`로 바꿨다.**

사용자가 바뀌면서 반복해서 볼 축도 바뀌었다. 소싱 담당자는 항공사 단위로 협상하므로
항공사를 고르는 게 맞다. `airline`이 `text`라 집계가 안 돼서 `.keyword` 서브필드를 썼다.

**4. `total_price` range slider를 넣지 않았다.**

가격이 노선·등급과 무관하게 퍼져 있어서 범위를 좁혀도 의미 있는 부분집합이 안 나온다.
대신 가격 구간 × 도착지 Table로 분포만 보여준다.

**5. "출발 시간대별 항공권 수" 차트를 빼고 숙박일수 차트로 대체했다.**

`out_dep_time`은 출발 예정일이지 판매일이 아니다. 시간축 차트를 넣으면 Day 4가 반복해서
경고하는 "`created_at`을 판매 추이로 읽는 오류"를 그대로 저지르게 된다. 그래서 시간축을
아예 빼고 숙박일수 분포로 바꿨다.

**6. 계획에 없던 차트를 4개 더 만들었다.**

Donut(항공사 비중), Table(가격 × 도착지), Tag cloud(도착지), Heatmap(항공사 × 도착지).
차트 종류를 다양하게 써보는 것도 이번 실습 목적이라 넣었다. 다만 Heatmap은 30칸 값이
303~375에 몰려 있어 색 차이가 난수 변동이다. 이 점은 `dashboard-review.md` 5절에
"노선 편중으로 읽으면 안 된다"고 적어뒀다.
